# バージョニング規則

## バージョン番号形式

`メジャー2桁.マイナー2桁.デバッグ2桁`（例：`01.01.00`）。初期値は `01.01.00` とする。

| 区分 | 意味 | 刻む基準 |
|---|---|---|
| メジャー | 破壊的変更・`requirements.md` の要件定義そのものを変更する節目 | 要件定義の変更を伴う場合 |
| マイナー | 機能追加（F1〜F10等の新規実装・拡張） | 新機能・既存機能の拡張時 |
| デバッグ | 不具合修正・軽微な調整 | バグ修正・文言修正等 |

`package.json` の `version` フィールドは npm の SemVer 検証と衝突するため `0.0.0` に
固定し、プロダクトバージョンはこのファイルとGitタグで管理する。

## タグ形式

**必ず注釈付きタグ**を使う（軽量タグ禁止）。

```
git tag -a v01.01.00 -m "リリース内容の要約"
git push origin v01.01.00
```

タグメッセージには対象範囲（対応するIssue/PR番号、主な変更点）を要約して含める。

## リリース時の必須添付物

GitHub Release作成時、次を添付する。

- 対象PRの一覧
- `code-review` 〜 `audit & security-gate` の結果を1枚にまとめたPDF（`report`、
  [CONTRIBUTING.md](../CONTRIBUTING.md) の開発フロー参照。作成はClaude Desktop側で行う）
- 変更影響（該当する場合。`requirements.md` 4.6節の変更影響の考え方に準じる）

添付物が揃っていないリリースは、監査上「判定不能」として扱い、正式版として承認しない。

## 検証・承認記録

レビュー・監査の結果は `WORK/`（非公開・バージョン管理下）にバージョン番号・日付付きで
残し、Release本文からリンクする。これにより、いつ・誰が・何を検証したかを版管理対象の
ログとして追跡できるようにする。

## リリースフロー

詳細は [CONTRIBUTING.md](../CONTRIBUTING.md) の「開発フロー全体像」を参照。
GitHub Releasesの発行（`published`）をトリガーに、audit & security-gateをClaude Desktop側で
実施し、実デプロイもClaude Desktop側で行う（CI側はリリース内容の形式検証のみ行う）。
